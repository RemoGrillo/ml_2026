generative models · 01machine learning vs in-context learning

Two ways to teach a model a task.

fine-tuning (notebook 4)

Learning = changing the weights with gradient descent.

cost

Labelled data, GPUs, time. The result persists in a new model.

in-context learning (today)

Learning = conditioning on the prompt. The input changes, the output follows; no weight moves.

cost

Only tokens. Nothing persists: the next call starts from zero.

The learning already happened elsewhere: pre-training, then instruction tuning / RLHF — done by someone else, out of our control.
Left: what we did last time. Labelled data goes into a training loop and the weights change; the result is a new model. Right: today. Watch the two animations: on the left the weights keep flickering, on the right the input changes ("Sonnets", "Rome diary"...) and the output changes with it, while the weight grid stays perfectly still. The model's weights are frozen. All the "learning" happens inside the prompt: we write instructions and maybe a few examples, and the model conditions on them for one call. Next call, it has forgotten everything. The real learning happened at pre-training and at the instruction-tuning/RLHF stage, which we don't have access to.
generative models · 02zero-shot · few-shot

In context, the examples are the training set.

SYSTEM You label 19th-century book titles by genre. USER Title: "Poems, chiefly in the Scottish dialect" Genre: poetry Title: "A journey through the Highlands" Genre: travel Title: "The history of the county of Durham" Genre: history ← the model completes
Two solved examples + one open case = a few-shot prompt. Remove the examples: zero-shot.
zero-shot

Instructions only. Fine for tasks the model already “knows”.

few-shot

Add 2–5 solved examples: labels and format become explicit.

for one call only

Examples live in the context window — and on the bill.

A concrete case with the British Library book titles from the course data. The two solved examples act as a tiny training set, but only for this call. Zero-shot: just the instruction. Few-shot: instructions plus examples; this is often the cheapest way to fix format problems. The price: examples are tokens, they take room in the context and they are paid for on every call.
generative models · 03architectures

Most chat models are decoder-only.

BERT · notebook 4

Reads the whole text at once. Good for classifying and embedding.

original transformer · T5

Encoder reads the source, decoder writes the target.

GPT · Llama · Mistral · Gemma · Qwen

One stack, trained only to predict the next token.

Three families of Transformer. BERT, which you fine-tuned, is encoder-only: every token attends to the left and the right, which is great for understanding and classification, but it cannot write. The original 2017 Transformer is encoder–decoder, built for translation. Today's chat models (GPT, Llama, Mistral, Gemma, Qwen) are decoder-only: a single stack that only attends to the past and is trained on one objective, predict the next token.
generative models · 04causal attention mask

Each token sees only the past.

rows: the token being processed · columns: what it may attend to
causal mask

Each row may look at its own column and those to the left. Everything above the diagonal (×) is blocked.

example · the row “digitised”
The archive was digitised in 1998.

Its training target is the next word, “in”. If it could see “in”, it would copy the answer instead of learning to predict it.

training

Every position predicts its next token: one text = many training examples.

generation

When writing, the future does not exist yet. Each new token is computed from the tokens already written, then becomes part of them.

This is what "decoder-only" means mechanically. The grid fills row by row, slowly: read it as "when processing this word, which words may I look at?". The orange row is the example on the right. In the attention matrix, the row for "digitised" can look at "The", "archive", "was" and itself, never at "in" or "1998". During training this lets every position in a text be an example at once: predict token 2 from 1, token 3 from 1–2, and so on. During generation, it means the model never needs anything to the right of where it is writing.
generative models · 05autoregressive sampling

Generation is a loop: one token at a time.

step 1
 
Probabilities are illustrative. Real vocabularies have 32k–260k tokens.
This runs on its own. At each step the decoder reads the whole sequence so far and outputs a probability distribution over the vocabulary for the next token. One token is picked, appended, and the loop repeats. Point at step 4: the model picks " notary" even though " scribe" is more likely. That is sampling: it does not always pick the top token. This loop is also why generation is slow and why output tokens cost more, which we'll see in part four.
generative models · 06temperature

Temperature reshapes the distribution before sampling.

“The manuscript was written in …”
T1.00
pi = exp(zi / T) / Σj exp(zj / T)
T → 0

Greedy: always the top token. Use it for extraction.

T = 1

The model's own distribution, unchanged.

T > 1

Flatter: more variety, more nonsense.

caveat

T = 0 on an API is best-effort, not a guarantee of identical outputs.

Interactive: drag the slider or click the presets, then "sample ×12" to draw twelve tokens at the current temperature. Temperature divides the logits before the softmax. Below 1 it sharpens the distribution, at 0 it collapses onto the top token (greedy decoding). Above 1 it flattens it, so rarer tokens appear. For metadata extraction we use temperature 0. Even then, APIs can return slightly different outputs across calls: click "why?" for the explanation (floating point, batching, near-ties amplified by autoregression, silent model updates). Esc closes it. We come back to this under reproducibility.
generative models · 07tokens

Models read text as tokens.

clean English — 7 tokens

The manuscript was digitised in 1998.

Italian — 10 tokens

Il manoscritto è stato digitalizzato nel 1998.

noisy OCR — 14 tokens

The man of cript wa s dig ni fied in 19 9 8.
rule of thumb

English: ~4 characters per token. Other languages, code and OCR noise: more.

the unit of everything

Context size, speed and price are all counted in tokens.

caveat

Splits are illustrative: every model has its own tokenizer.

Models don't see words but sub-word pieces. Frequent English words are single tokens; rarer words and other languages get split ("mano" + "scritto"). OCR noise is worse: "manuscript" read as "man of cript", spaces inserted inside words, digits split: every fragment becomes its own token, and "of" is now a real, misleading word. The same sentence with OCR errors can cost twice as many tokens, which matters for both context and money when you process a whole digitised collection. The exact split depends on each model's tokenizer; what's on the slide is illustrative.
generative models · 08context window

The context window is a container: every turn fills it.

8,192 tokens
 
systemyou (+ documents)modelroom for the answer
everything counts

System prompt, every question, every document, every answer — and room for the next answer.

it only grows

Each call resends the whole conversation. Nothing is forgotten until it no longer fits.

overflow

APIs return an error. Ollama silently drops the oldest turns.

The context window is the maximum number of tokens processed in one call, input plus output together. Left: the container, 8,192 tokens. Centre: a research chat on two letters from the Datini archive. Every message lands in the container with a height proportional to its tokens: the attached OCR letters are the big orange blocks. The model has no memory between calls: each turn resends everything, so the container only grows. At the last question there is no room left for the answer. An API would stop with an error. Ollama instead silently drops the oldest messages, here the first letter, and answers anyway: "I can't find any debt to Stoldo", which is wrong, because the debt was in the letter it just threw away. It only says so in its logs. That is why long chats and long RAG prompts sometimes "forget" the documents.
generative models · 09auto-compact

Auto-compact: an endless chat, paid for in details.

8,192 tokens
compact at 85%
 
systemyou (+ documents)modelsummary
the trick

Near the limit, the model summarises the older turns; the summary replaces them.

feels infinite

The container never overflows: the conversation can go on for ever.

what was lost
    Same conversation, same container, one change. A threshold at 85%: when the container crosses it, the older turns are sent to the model with the instruction "summarise this", and the summary replaces them. ChatGPT, Claude, coding agents all do some version of this. The container drops back to a third full and the chat can continue indefinitely. But a summary is a lossy compression decided by the model: the full text of both letters is gone, and so are the details it judged unimportant, like the 40-florin debt to Stoldo. When we ask about the debt, the model now honestly says the summary doesn't mention it. Better than the silent truncation on the previous slide, but the information is still gone. For research work: keep the sources outside the chat and bring back the relevant passages when needed. That is exactly what RAG does.

    local vs APIs · 01local model

    Local: the request stays home.

    same interface

    Messages in, tokens out — often the same client library.

    provider APItwo places to run a model

    API: the request leaves.

    different deal

    Who holds the weights, the data, and the bill.

    Two places a request can go, one per half. Left, black: everything happens inside the dashed fence of your machine. Your code sends the request (filled dots) on localhost to a runtime that has loaded open weights from your disk, and the answer (hollow dots) comes back without ever leaving: unplug the network and it still works. Right, orange: the fence now contains only your code. Every request crosses it, carrying your prompt and your documents to the provider's datacenter, where weights you cannot see or download (the black box with the scrambled bytes) produce the answer, which travels back. From the code's point of view the two look almost identical: a list of messages goes in, tokens come out. What differs is who owns the weights, where your data goes and who sends you the bill.

    local vs APIs · 06API keys · generate

    An API key is a password that spends your money.

    provider console › API keys
     
    what it is

    A long random string. It says who you are and whose account pays. Whoever holds it, spends.

    generate

    Provider console → API keys → Create. One key per project or machine, named so you recognise it.

    shown once

    The full key appears only at creation. Afterwards the console shows the last few characters. Lost it? Make a new one.

    limit the damage

    Spending cap, only the permissions you need, an expiry date if offered.

    Before storing keys, what they are. An API key is a bearer token: a long random string sent with every request, which tells the provider who you are and which account to bill. There is no second factor: whoever has the string can spend your credit. The animation follows the life of a new key in a generic provider console. You create it from the dashboard, giving it a name (one key per project or per machine makes it easy to know which one to revoke), and where possible restricting permissions, setting a monthly spending cap and an expiry. Then the key is displayed exactly once. When the dialog closes, the console only stores a hash: from now on you see "sk-…Q8xZ", the last few characters, and nobody, not even the provider, can show you the full key again. If you didn't copy it, you don't recover it: you create a new one and delete the old.

    Rotation means replacing a key with a new one before the old one is revoked. The playhead runs along six months. Key A has been in use since day 0. At step 1 you create key B. Step 2: you replace A with B everywhere it is used: your .env, a server, a Colab notebook, a colleague's machine. Step 3: you test; during this overlap both keys are valid, so nothing breaks. Step 4: you revoke A. Revocation is immediate and final: any program still using A starts failing with a 401 Unauthorized, which is actually useful because it shows you where the key was still hiding. When to rotate: on a schedule, every few months or when someone leaves the team; immediately whenever the key may have been exposed. And keys disappear on their own too: expiry dates, providers deleting unused keys, a finished free trial. Code should fail clearly on a 401, not silently.

    local models · 05reproducibility

    Reproducibility: weights don't get retired.

    APIs: best effort

    Even at T = 0: batching, floating point, silent updates, retirements.

    locally: pin it

    Weights file + hash, runtime version, prompt, temperature, seed.

    the standard

    A result in a paper should still run in five years.

    An API model is a moving target. Providers update models behind the same name and retire old versions, and even at temperature zero outputs can vary across calls because of batching and floating-point effects. With local weights you can archive the exact file, record its hash, the runtime version, the prompt and the sampling parameters. Hardware differences can still introduce small variations, but you control the variables. If you publish results produced by an LLM, this is the difference between a reproducible method and an anecdote.

    attention needs the past

    Each new token is compared with the keys and values of all previous ones.

    keep, don't recompute

    Store K and V for every token, in every layer: memory traded for time.

    size per token

    2 × layers × KV heads × head size × bytes. Llama 3.1 8B: 128 KiB.

    No tool reports it. You can only time it.

    What fills the room. In every layer, every token produces a key and a value vector; attention compares each new token's query with all previous keys and mixes their values.     decode = writing

    What prefill and decode mean, in the one place everyone has met them: a chat. You paste the OCR of a letter, about 540 tokens, and ask a question: a 600-token prompt. First nothing happens, only the three dots: that is prefill. The model is reading the whole prompt, and because all of it is already there, every token goes through the network at the same time, in parallel. On this laptop that is about 590 tokens per second, so about one second of waiting: the "time to first token". Then the answer appears word by word: that is decode. The model cannot write token 2 before token 1 exists, so it goes one token per step, about 47 per second, and 120 tokens take two and a half seconds. Two practical consequences: a longer pasted document makes the pause longer; a longer answer makes the stream longer. The next slide shows why the two speeds are so different.
    under the hood · 07prefill vs decode · inside

    Prefill vs decode: reading is parallel, writing is serial.

    prefill≈ 590 tok/s
    weights read 1×
    decode≈ 47 tok/s
    weights read 0×
    prefill

    All prompt tokens through the network at once: big matrix products, compute-bound.

    decode

    One token per step, and each step reads all the weights again: memory-bound.

    hence the prices

    Input is billed 4–6× cheaper than output. Time-to-first-token = prefill.

    40 tokens per lane, slowed down; the 12× ratio is the one measured on the previous slide.
    The same two phases, from inside the model. Two phases with very different physics. Prefill: the whole prompt is known, so all its tokens go through each layer together as one large matrix multiplication; the GPU is busy computing, and it's fast. Decode: each new token depends on the previous one, so it's one token per step, and every step has to stream all the model's weights from memory to compute a single token. Memory bandwidth, not compute, is the limit. That's why time-to-first-token depends on prompt length, why output streams slowly, and why every provider prices output tokens several times higher than input.
    under the hood · 08quantization

    Quantization: fewer bits per weight.

    bits  
    FP16float · sign + exponent + mantissa
    BF16float · more range, fewer digits
    Q8integer + 1 scale per block
    Q6integer + scale
    Q4integer + scale · the usual pick
    signexponentmantissainteger
    FP16
    Floating Point, 16 bits. Like scientific notation: sign, exponent (how big), mantissa (the digits). Models are trained and released like this.
    BF16
    Brain Float 16 (Google Brain): same 16 bits, more exponent, fewer digits. Wide range, less detail.
    FP32
    Full precision, 32 bits: what training uses. Twice FP16.
    Q8 · Q6 · Q4
    Quantized to 8, 6, 4 bits: each weight becomes a small integer; one scale per block of ~32 weights restores the size.
    Q4_K_M
    GGUF naming. 4 bits · K = k-quant, blocks inside super-blocks · S / M / L = small, medium, large: how many sensitive layers keep extra bits.
    GGUF · MLX
    File formats: GGUF for llama.cpp, Ollama, LM Studio; MLX for Apple Silicon.
    the trade

    Q8 ≈ lossless, Q6–Q5 safe, Q4 the usual sweet spot; below, quality drops.

    size of an 8B model

    16 GB at FP16 · 8.5 at Q8 · 4.8 at Q4

    Precision here = numerical precision of each weight, not precision-and-recall. Grey: original weights. Red: what survives with 2bits levels. Real formats (GGUF Q4_K, MLX 4-bit) quantize small blocks, each with its own scale, so the error is smaller than shown.
    Quantization stores each weight with fewer bits. First the acronyms, on the right. FP16 is a 16-bit floating-point number, like scientific notation in binary: one sign bit, five exponent bits that say how big the number is, ten mantissa bits for the digits (the strips under the chart show the layout). BF16, "brain float" from Google Brain, keeps the same 16 bits but moves them: eight for the exponent, seven for the digits, so it covers a much wider range with less detail; it is common in training. FP32 is full precision. The Q formats are quantized: each weight becomes a small integer, and one scale factor per block of about 32 weights brings it back to the right magnitude. In GGUF names like Q4_K_M, K means k-quants (blocks grouped in super-blocks, each with its own scale) and S, M, L say how many of the most sensitive layers are kept at higher precision. The strips are clickable too. The word has nothing to do with precision and recall: it's numerical precision. Click the buttons: with 8 bits you have 256 levels and the red line is indistinguishable from the grey; at 4 bits, 16 levels, you see steps; at 2 bits only 4 levels. Real formats are smarter than this toy: they quantize blocks of 32 or 64 weights, each block with its own scale, so the error is much smaller. Practical rule: Q8 is essentially lossless, Q6 and Q5 safe, Q4 the usual compromise, below Q4 quality degrades noticeably. And the size halves at each step.

    Will it fit? Weights + KV cache + system.

    rule of thumb

    4-bit weights ≈ parameters (in billions) × 0.6 GB.

    plus

    where it lives

    Apple Silicon: one shared pool. Discrete GPU: past VRAM, layers spill to CPU and slow sharply.

    under the hood · 11mixture of experts

    Mixture of experts: everything stored, little used.

     
    qwen3-35b-a3b
    35b

    total parameters, all experts → decides memory: ≈ 20 GB at Q4.

    a3b

    active per token → decides speed: about as fast as a 3B.

    the picture

    A hospital with 128 specialists: each patient sees 8, but all 128 must be on the payroll.

    not topic experts

    No “Latin expert”: the router learns its own split, token by token, layer by layer.

    other spellings

    8x7B: 8 experts, 2 per token (Mixtral: ~47B stored, ~13B active).

    A dense model uses every parameter for every token. A mixture-of-experts model replaces the big feed-forward block of each layer with many smaller "experts" and a router. Watch the animation: each word of the sentence arrives at the router, which sends it to two of the eight experts; only those two compute, then their outputs are combined and passed to the next layer. The small counters show that over a sentence the work spreads across all experts, so all of them must be loaded in memory, even though each token only uses a quarter of them. Real models have 64 to 128 experts with about 8 active. That is what the name encodes. In qwen3-35b-a3b, "35b" is the total: all experts, which is what has to fit in memory, about 20 GB at 4 bits. "a3b" means 3 billion active per token, which is what sets the speed: it writes about as fast as a 3B dense model. The analogy: a hospital with 128 specialists, every patient sees 8, but you pay all 128. Careful: experts are not topic specialists; the split is learned and not human-readable. Older naming: Mixtral 8x7B, eight experts of roughly 7B, two active, about 47B stored and 13B active because attention layers are shared.

    temperature 0 · why not identical?

    T = 0 picks the top token. The top token itself can change.

    1 · floating point

    On a GPU, (a + b) + c ≠ a + (b + c) in the last digits. Sums are split across thousands of threads, and the order is not always the same.

    2 · batching

    Your request is processed together with other users' requests. A different batch → different kernels and summation order → slightly different logits.

    3 · near-ties

    Usually harmless. But when two tokens are almost tied (say 0.4001 vs 0.3999), a tiny change flips the winner…

    4 · autoregression

    …and the flipped token becomes context for every later step: from there on, the two texts diverge.

    5 · the model itself

    Providers update models behind the same name; some mixture-of-experts routing depends on the batch too.

    locally

    Same weights, same software, same machine, one request at a time: usually identical, run after run.
